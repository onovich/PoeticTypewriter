# Poetic Typewriter 项目认知

## 文档目的

这份文档用于沉淀当前项目的长期有效认知，重点记录项目定位、现状、架构边界、视觉与交互基线、开发与部署事实，以及后续扩展时不应轻易破坏的约束。

## 项目一句话

Poetic Typewriter 是一个以“复古拟物打字机 + 气球化字符 + 短诗输入”为核心体验的 Web 小游戏，目标不是效率型打字训练，而是偏情绪体验、节奏感和视觉反馈的诗意交互作品。

## 当前项目状态

- 原始单文件原型保留在 `origin/`，它仍然是理解原始交互、视觉细节和回退行为的第一参考源。
- 当前工程已经完成从单文件原型到 Vite 工程的基础迁移，具备 `index.html`、`src/main.js`、`src/App.js`、`package.json`、`vite.config.js` 等完整入口。
- 当前分层属于“可迁移准备已建立”，不是“完全解耦完成”。
- Git、远端仓库和 GitHub Pages 已接通，部署链路可用。

## 目录职责

### `origin/`

- 存放原始原型和设计交接文档。
- 这里不是未来主开发目录，但在需要校对像素、交互节奏和细节行为时，应优先回看这里。

### `src/data/`

- 存放诗句数据、键盘布局、阶段常量、时间参数。
- 这层更接近未来 Unity 可复用的数据定义层。

### `src/logic/engine/`

- 当前核心行为都集中在这里，尤其是 `TypewriterEngine`。
- 包含输入推进、气球生命周期、阶段切换、位移与旋转计算、线条弯曲计算。
- 这是后续继续抽纯逻辑的主要入口。

### `src/logic/hooks/`

- 当前主要承担“应用装配”和“浏览器事件桥接”的职责。
- 这里负责把 DOM 元素、事件监听和引擎连接起来。

### `src/view/`

- `screens/` 负责页面骨架。
- `components/` 负责键盘等可拆分视图片段。
- 当前视图层仍然输出字符串模板，不是组件化框架视图。

## 交互基线

- 核心体验不是“打字输入本身”，而是“输入触发视觉物理结果”。
- 输入正确与错误都要有明确反馈，错误字符不是简单忽略，而是也会升空并以错误样式存在。
- 退格不是纯文本删除，而是一个物理拉回动作。
- 整句完成后的节奏必须保留四段式体验：等待、收线、悬浮、吹散。
- 物理键盘与屏幕键盘必须共享同一套行为逻辑，避免两套输入路径出现节奏不一致。

## 设计与美术基线

- 视觉关键词是：暗色、复古、拟物、安静、文学感。
- 打字机机身、按键、阴影、渐变和字体组合不是装饰细节，而是作品气质的一部分。
- `Playfair Display` 承担整体文学气质，`Special Elite` 承担打字机感和字符实体感，这个搭配是当前视觉识别的重要基础。
- 主要动态表现依赖逐帧 JS 计算，而不是依赖一组固定 CSS 动画，这一点对“风吹”“摇摆”“漂散”的自然感很重要。
- 若未来做视觉升级，优先增强材质层次、氛围和声音，而不是先把界面做得更“现代扁平”。

## 当前架构认知

### 已经抽离出来的部分

- 诗句数据、键盘布局和阶段时间参数已经从原型中抽出到数据层。
- 主要行为状态机已经集中到 `TypewriterEngine`，避免散落在多个脚本片段里。
- 视图骨架和键盘结构已经单独拆出，便于替换表现层。

### 还没有完全抽干净的部分

- `TypewriterEngine` 仍然直接创建和修改 DOM 节点，也直接写入 style。
- 这意味着当前 `engine` 仍然是“逻辑 + 渲染耦合”的混合层，而不是纯模拟层。
- 如果后续要做更深的重构，优先方向不是继续拆目录，而是把“状态推进”和“DOM 渲染”进一步分开。

### 目前这种状态的价值

- 保留了原型行为的稳定性。
- 把后续重构的入口位置收拢到了少数文件里。
- 已经为未来迁移到 Unity、Canvas、SVG 强化版、甚至 React 组件视图提供了边界基础。

## 开发与部署事实

- 运行方式：`npm install`、`npm run dev`、`npm run build`、`npm run preview`。
- 当前使用 Vite 构建，`base` 配置为 `/PoeticTypewriter/`，适配 GitHub Pages 仓库子路径部署。
- GitHub Pages 工作流已经存在，使用 GitHub Actions 自动构建和发布。
- 当前线上访问存在一层跳转：GitHub Pages 地址会跳到自定义域名路径。
- 这意味着后续如果线上访问异常，不能只检查仓库本身，还要一起检查 GitHub Pages 设置和域名映射链路。

## 在线挑战演进决策

- 项目后续将拆分为“自由模式”和“每日挑战模式”。
- 自由模式继续保留当前纯前端、本地数据、无全站排行的作品属性。
- 每日挑战模式将引入轻量服务端，承载每天 100 条内容、成绩提交、当日最佳、历史最佳和全站排名。
- 每日挑战前端现已在页面内直接显示最近成绩、当日最佳、历史最佳和两个排名，不再只依赖 `document.title` 或调试桥观察运行态。
- Web 前端代码默认可被浏览器看到，因此安全边界不能建立在“前端代码不暴露”之上。
- API 地址可以是公开信息，但数据库密钥、签名密钥和管理员令牌不能进入前端。
- 若仓库未来转为私有，免费 GitHub Pages 不再是长期可依赖的线上托管方案。
- 因此，在线挑战模式的目标托管方向应从“GitHub Pages 静态站”演进为“独立静态前端 + 独立 API 服务”，并优先考虑可通过 CLI 自动化部署的轻量方案。
- 详细方案见 `docs/ONLINE_COMPETITION_ARCHITECTURE.md`。

## 当前已知边界与风险

- 当前依赖 `tailwindcss.com` CDN 注入工具类，适合轻量项目，但不适合后续做复杂设计系统或离线可控构建。
- `TypewriterEngine` 直接持有 DOM 元素，会让单元测试、纯逻辑复用和非 DOM 渲染目标变得更难。
- 当前 `Math.random()` 直接参与视觉效果，会降低可复现性和自动化测试友好度。
- 目前没有音效、统计、可配置诗句源和横屏专项适配，这些会影响完整产品感。
- 当前项目更像“稳定可运行的体验原型工程”，还不是“长期规模化功能开发工程”。

## 后续重构建议

- 第一优先级不是更换框架，而是把 `TypewriterEngine` 中的纯状态推进与 DOM 更新拆开。
- 可以引入 `BalloonModel`、`PhaseController`、`BalloonRenderer` 这样的更细粒度对象，但要避免一上来过度抽象。
- 若后续要做 React 化，应保持“React 管装配、engine 管规则、renderer 管具体绘制”的边界，而不是把物理逻辑重新塞回组件状态。
- 若未来要迁移到 Unity，可优先迁移数据结构、阶段状态机、气球生命周期和位移公式；浏览器事件与 DOM 渲染部分则应视为平台层。

## 后续扩展方向

- 音效系统：键盘、空格、删除、整句完成铃声。
- 数据统计：WPM、正确率、输入节奏可视化。
- 诗句来源扩展：本地存储、自定义输入、远端配置。
- 在线挑战：每日 100 条内容、匿名成绩提交、当日与历史排行榜。
- 物理增强：字符碰撞、风场扰动、分层景深。
- 适配增强：移动端横屏、不同屏宽下的键盘比例控制。

## 工作约定

- 需要校对体验时，先对照 `origin/index.html` 与 `origin/design.md`。
- 需要改交互节奏时，先看 `src/data/config.js` 和 `src/logic/engine/typewriterEngine.js`。
- 需要改页面结构时，先看 `src/view/screens/typewriterScreen.js` 和 `src/view/components/keyboard.js`。
- 不要把 README 当成内部知识库；README 面向仓库访问者，而这份文档面向后续维护者。
