# Poetic Typewriter 会话记录（2026-05-08）

## 本次会话完成了什么

- 为项目建立了本地 Git 仓库并接上远端仓库。
- 将单文件原型整理为可运行的 Vite 工程。
- 按 `data / logic / view` 方向做了第一步分层。
- 补齐了 README、`.gitignore`、GitHub Pages 工作流和构建配置。
- 完成了本地构建验证、远端推送和线上页面验收。

## 本次会话对交互的经验与教训

- 这个项目最值钱的不是“实现了输入”，而是“输入如何变成一段有节奏的演出”。
- 删除键必须保留物理惩罚感，不能退化成普通文本编辑器的删除体验。
- 正确字符和错误字符都要被实体化，这会让输入行为更有重量感，也更符合这个项目的美学方向。
- 两套输入方式必须统一走同一套引擎，否则很容易出现手感割裂。
- 完成整句后的停顿很重要。没有这段停顿，作品会更像一个小游戏界面，而不是一个有呼吸感的作品。

## 本次会话对设计与美术的经验与教训

- 这类项目不能被“工程化重构”顺手削平成普通网页。
- 阴影、渐变、字体、压键位移、纸口位置、字符漂浮感，都是体验骨架，不是可有可无的装饰。
- 比起补更多界面模块，这个项目更适合继续强化氛围层：音效、风感、停顿、材质、模糊和节奏。
- 当前视觉语言已经很明确，后续扩展应沿着“更细腻”走，而不是沿着“更现代”走。

## 本次会话对开发流程的经验与教训

- 有原型源码不等于有工程。先补脚手架，再谈重构，这是这次最重要的流程教训之一。
- 在非空目录里做工程初始化时，必须检查入口文件是否真的落盘，不能只看命令是否跑过。
- 构建链路必须先本地跑通，再做 GitHub Pages，不要把 CI 当调试器。
- GitHub Pages 若走仓库子路径部署，`vite.config.js` 的 `base` 是高频坑位。
- 远端验收不能只看 `github.io` 地址，也要检查是否存在自定义域名跳转。

## 本次会话对重构的经验与教训

- 这次重构最合理的目标不是“全量框架化”，而是“先把未来能继续拆的边界立住”。
- 目录拆分本身不代表重构完成，真正的价值在于行为是否被收束到了可控边界。
- 当前最值得继续推进的不是再拆一个目录，而是把 `TypewriterEngine` 中的模拟逻辑和 DOM 渲染分离。
- 保留原型可回退版本非常重要，这让重构可以更大胆，但不至于丢失原始体验。

## 对后续拓展的思考

### 适合尽快做的

- 音效系统，因为它对体验提升大、风险低。
- 数据统计，因为它能补足“玩一次之后还想继续玩”的反馈层。
- 自定义诗句输入，因为它能显著提升可玩性和分享性。

### 适合在第二阶段做的

- 横屏与移动端布局专项调整。
- 更细的物理表现，例如气球间相互扰动、风向波动、细线张力变化。
- 将渲染逻辑从引擎中拆出，为 Canvas 或 Unity 迁移做准备。

### 暂时不建议优先做的

- 盲目换成重框架或过度组件化。
- 在没有明确收益前引入复杂状态管理库。
- 为了“更现代”而破坏现有拟物风格。

## 当前潜在风险

- 现有引擎仍然带有明显 DOM 耦合，继续堆功能会提高后续拆分成本。
- 当前依赖 Tailwind CDN，未来若要加强可控性、离线能力或构建优化，最好迁移到本地样式方案。
- 线上页面当前存在域名跳转链路，这意味着未来排查线上问题时要同时看仓库配置和域名配置。
- 当前没有自动化测试，后续如果交互逻辑继续增长，回归验证成本会逐步上升。

## 如果下一次继续做，建议从这里开始

- 先明确下一次目标是“增强体验”还是“继续重构”，不要两条线同时发散。
- 如果目标是体验增强，优先做音效和统计。
- 如果目标是结构演进，优先拆 `TypewriterEngine` 的渲染耦合。
- 如果目标是产品化，优先补自定义诗句、设置面板和移动端适配。

## 给未来维护者的提醒

- 不要轻易删掉 `origin/`。
- 不要把当前文档中的“已建立迁移基础”误读成“已经完成彻底解耦”。
- 不要只从代码结构判断项目质量，这个项目的核心质量很大一部分体现在动态节奏、视觉氛围和输入手感上。
